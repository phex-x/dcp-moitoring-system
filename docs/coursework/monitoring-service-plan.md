# План реализации Monitoring Service

## Цель и границы

Monitoring Service отвечает за инфраструктуру ЦОД, источники телеметрии, приём и хранение энергетических измерений, оперативные агрегаты и публикацию событий. У сервиса отдельное Spring Boot-приложение и отдельная база `monitoring_db`. Он не обращается к базам Auth и Ecology и не содержит бизнес-логику Gateway.

В рамках первой итерации предполагается Java 21, Spring Boot 3.5.16, Maven, Spring Web, Validation, Data JPA, PostgreSQL, Liquibase, Kafka и Actuator. Схемы и API держим совместимыми с ТЗ и общими правилами в `AGENTS.md`; изменения контрактов оформляем отдельно.

## Предлагаемая структура модуля

```text
services/monitoring-service/
├── pom.xml
└── src/
    ├── main/
    │   ├── java/com/bank/dcp/monitoring/
    │   │   ├── MonitoringServiceApplication.java
    │   │   ├── config/             # конфигурация приложения, OpenAPI, Kafka
    │   │   ├── common/             # общие ошибки, Problem Details, correlation id
    │   │   ├── datacenter/         # ЦОД и стойки
    │   │   │   ├── controller/
    │   │   │   ├── dto/
    │   │   │   ├── entity/
    │   │   │   ├── mapper/
    │   │   │   ├── repository/
    │   │   │   └── service/
    │   │   ├── server/             # серверы и метаданные ресурсов
    │   │   ├── measurement/        # измерения, фильтры, ряды и агрегаты
    │   │   ├── source/             # источники и проверка доступности
    │   │   ├── collector/          # интерфейс коллектора, симулятор и задания
    │   │   ├── kafka/              # события, outbox publisher
    │   │   └── dashboard/          # read-модели/сводные запросы
    │   └── resources/
    │       ├── application.yml
    │       └── db/changelog/       # Liquibase changelog и миграции
    └── test/
        └── java/com/bank/dcp/monitoring/
```

Пакеты добавляются по мере реализации; на старте не создавать пустые классы под все возможные функции. DTO REST и Kafka-контрактов не должны раскрывать JPA-сущности.

## Этапы реализации

### 0. Зафиксировать контракты и настройки

- Сопоставить таблицы, поля, статусы, фильтры и endpoints из разделов 8, 10, 21 и 26 PDF с каркасом.
- Согласовать точные правила статусов для ЦОД/стоек/серверов/источников и поведение удаления (предпочтительно деактивация при наличии истории).
- Утвердить поля обязательных запросов, единицы измерений (W, kWh, проценты, °C), UTC и правила округления.
- Зафиксировать Kafka topic и envelope событий: `eventId`, `eventType`, `eventVersion`, `occurredAt`, `aggregateId`, `payload`.
- Принять решение о выборе Liquibase, используемом ТЗ; не добавлять миграции через Hibernate `ddl-auto`.
- Результат: короткий ADR/контракт, согласованные конфигурационные ключи и список API первой версии.

### 1. Запускаемый сервис и конфигурация

- Проверить Maven-модуль, главный класс, Java toolchain и согласованность Spring Boot версии с корневым BOM.
- Добавить профили локальной разработки и тестов; конфигурацию получать через переменные окружения.
- Настроить отдельное подключение к `monitoring_db`, health/info/metrics endpoints Actuator.
- Добавить единый формат ошибок Problem Details с `code`, `traceId`, `timestamp` и деталями валидации.
- Добавить OpenAPI и базовые метаданные сервиса.
- Результат: сервис запускается отдельно и сообщает health; при недоступности БД поведение диагностики понятно.

### 2. Модель инфраструктуры и миграции

- Создать Liquibase changelog для `data_centers`, `racks`, `servers`.
- Добавить UUID ключи, UTC timestamp-поля, ограничения, уникальность кодов/hostname/asset tag и индексы для связей.
- Реализовать entity/repository и DTO/mapper для каждой модели.
- Проверить правила ссылочной целостности внутри `monitoring_db`; никаких FK на чужие сервисы.
- Определить политику удаления и защиту от удаления объектов с измерениями.
- Результат: чистая база воспроизводимо создаётся миграциями.

### 3. CRUD API ЦОД, стоек и серверов

- Реализовать `/api/v1/data-centers`, `/api/v1/racks`, `/api/v1/servers`: list/get/create/patch/delete или deactivate согласно утверждённой политике.
- Добавить Jakarta Validation, проверку уникальности, корректные 404/409/422 и единый error contract.
- Списки сделать с серверной пагинацией и сортировкой; ограничивать допустимые поля сортировки.
- Передавать между уровнями DTO, не JPA entity.
- Результат: инфраструктура доступна через OpenAPI и проверяется вручную через REST.

### 4. Источники данных и журнал сборов

- Добавить `measurement_sources` и `collector_jobs` миграциями.
- CRUD/просмотр источников, проверка соединения, ручной запуск синхронизации и журнал запусков.
- Определить контракт `Collector` и первую реализацию simulator; реальные счётчики и произвольные внешние системы оставить за пределами MVP.
- Сохранять число принятых/отклонённых записей, статусы, ошибки и временные отметки задания.
- Обеспечить ограничение параллельного запуска одного source и устойчивость к недоступности источника.
- Результат: демонстрационный сбор можно запустить из API и увидеть его статус.

### 5. Приём и хранение измерений

- Создать таблицы `energy_measurements` и `server_metric_snapshots`, индексы по времени, серверу, источнику и качеству.
- Реализовать DTO, валидацию значений и времени, ручной одиночный и bulk импорт.
- Реализовать фильтры `page`, `size`, `sort`, `from`, `to`, `dataCenterId`, `rackId`, `serverId`, `sourceId`, `minPower`, `maxPower`, `qualityStatus`.
- Связи по ЦОД/стойке фильтровать через собственную модель Monitoring, без cross-service SQL.
- Продумать идемпотентность повторного импорта (например, стабильный checksum/ключ поступления) и понятный отчёт о частичном успехе bulk-запроса.
- Результат: измерения можно импортировать, листать, фильтровать и получать по ID.

### 6. Kafka и надёжная публикация событий

- Добавить `outbox_events` в `monitoring_db` и писать событие в ту же локальную транзакцию, что и измерение.
- Реализовать publisher с повторными попытками и состояниями доставки; Kafka не включать в распределённую транзакцию.
- Публиковать версионированные события `measurement.received` (при необходимости отдельно агрегаты) с UUID `eventId`.
- Описать топики и JSON envelope в `docs/kafka/`.
- Для будущих consumers предусмотреть at-least-once delivery и идемпотентность по `eventId`; не обещать exactly-once на уровне всей системы.
- Результат: сохранённое измерение надёжно попадает в Kafka после восстановления брокера.

### 7. Временные ряды, агрегаты и dashboard API

- Реализовать `/measurements/aggregate`, `/measurements/series` и сводные `/dashboard/overview`, `power`, `energy`, `server-health`.
- Согласовать временную гранулярность и правила суммирования: мощность — среднее/максимум в зависимости от показателя, энергия — сумма kWh за интервал.
- Рассчитывать PUE только при наличии необходимых входных значений; не подменять отсутствующие данные вымышленными.
- При необходимости добавить периодические агрегаты/кэш, оставляя PostgreSQL источником истины.
- Результат: frontend получает данные для графиков и обзорной панели.

### 8. Авторизация и взаимодействие с Gateway

- Определить способ передачи подтверждённой identity/roles от Gateway; Gateway и сервис должны защищать критические операции согласно принятой модели.
- Ограничить CRUD инфраструктуры STORAGE_ADMIN/ADMIN, чтение дать разрешённым ролям, ручной импорт — согласно PDF.
- Не доверять произвольным пользовательским заголовкам, если запрос не пришёл из доверенного Gateway/контекста.
- Уточнить локальный профиль разработки без встроенных production-обходов безопасности.
- Результат: endpoints имеют документированные и реально проверяемые ограничения доступа.

### 9. Демоданные, наблюдаемость и документация

- Подготовить повторяемый seed: несколько ЦОД, стоек и серверов, временные ряды и один намеренно недоступный источник.
- Настроить корреляционный ID в HTTP-логах и логах заданий/публикации событий; не писать токены и секреты.
- Описать env-переменные, порты, команды запуска, миграции и API в README/docs.
- Проверить Compose health checks и сценарий запуска с чистыми volume.
- Результат: воспроизводимый сценарий демонстрации Monitoring Service.

## Порядок feature-веток

Каждый следующий этап предлагается выполнять отдельной feature-веткой от актуальной `main`, после согласования объёма и мержа предыдущей:

1. `feature/monitoring-bootstrap` — зависимости, конфигурация, health, ошибки, OpenAPI.
2. `feature/monitoring-schema` — миграции инфраструктуры и сущности.
3. `feature/monitoring-infrastructure-api` — CRUD ЦОД/стоек/серверов.
4. `feature/monitoring-sources` — источники, simulator, collector jobs.
5. `feature/monitoring-measurements` — импорт и запрос измерений.
6. `feature/monitoring-outbox-kafka` — transactional outbox и событие измерения.
7. `feature/monitoring-dashboard-api` — агрегаты, временные ряды, overview.
8. `feature/monitoring-security` — роли и интеграция с Gateway/Auth.
9. `feature/monitoring-demo-data` — seed, документация и сценарий запуска.

## Критерии готовности сервиса

- Сервис стартует отдельно и подключается только к собственной `monitoring_db`.
- Чистая база создаётся Liquibase миграциями.
- CRUD инфраструктуры и API измерений соответствуют согласованным контрактам PDF.
- Валидация, пагинация, сортировка, фильтры и единые ошибки работают предсказуемо.
- События публикуются через outbox и имеют версию/idempotency key.
- Источник/collector демонстрирует сбор и обработку недоступности.
- Dashboard endpoints возвращают документированные показатели и не выдумывают отсутствующие значения.
- Health, метрики, correlation ID и документация доступны.
