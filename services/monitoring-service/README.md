# Monitoring Service

Отдельное Spring Boot-приложение для инфраструктуры ЦОД и энергетических измерений. Сервис владеет только базой `monitoring_db`; обмен с другими сервисами выполняется через API и Kafka.

## Структура кода

- `datacenter` — ЦОД и стойки.
- `server` — серверы.
- `measurement` — измерения, фильтры, агрегаты и временные ряды.
- `source` и `collector` — источники данных и сбор телеметрии.
- `kafka` — события и интеграция с брокером.
- `dashboard` — сводные read-запросы.
- `common` — общие типы и ошибки этого сервиса.

## Миграции

Liquibase changelog расположен в `src/main/resources/db/changelog/db.changelog-master.yaml`. У каждого микросервиса свой Liquibase changelog и собственная база; общий changelog или прямой запуск миграций одного сервиса в базе другого запрещены. Hibernate настроен на `ddl-auto: validate`, поэтому схему изменяют только миграции.

Параметры БД задаются через `MONITORING_DB_URL`, `MONITORING_DB_USERNAME` и `MONITORING_DB_PASSWORD`. Предметные таблицы создаются SQL-файлом миграции; откат схемы хранится отдельным SQL-файлом.

## API инфраструктуры

Реализованы endpoints ЦОД, стоек и серверов под `/api/v1`:

- `GET /data-centers`, `GET /racks`, `GET /servers` — постраничные списки (`page`, `size`, `sort`); размер страницы ограничен 100 записями.
- `GET /{id}` — получить объект.
- `POST /` — создать объект.
- `PATCH /{id}` — частично изменить переданные поля.
- `DELETE /{id}` — деактивировать объект, физическое удаление не выполняется.

Для инфраструктурных объектов статус передаётся значением enum `ACTIVE`, `INACTIVE`, `MAINTENANCE` или `DECOMMISSIONED`. Для источников, заданий сбора, качества измерений и outbox также используются отдельные enum-типы. Для стоек и серверов при создании и изменении родительский объект передаётся UUID-ом (`dataCenterId` или `rackId`), который разрешается в сервисном слое. Некорректные запросы возвращают Problem Details, отсутствующие объекты — 404, конфликты уникальности — 409. Защита endpoints ролями будет подключена отдельной интеграционной задачей вместе с Gateway/Auth.


## Источники и сбор телеметрии

- `/api/v1/sources` — постраничный список, получение, создание, частичное обновление и деактивация источника.
- `POST /api/v1/sources/{id}/test` — проверка готовности зарегистрированного коллектора для источника.
- `POST /api/v1/sources/{id}/sync` — синхронный запуск сбора; необязательное тело принимает `samplesPerServer` от 1 до 100.
- `/api/v1/collector/jobs?sourceId={uuid}` — история заданий, опционально с фильтром по источнику и серверной пагинацией.

Для `SIMULATOR` сборщик генерирует мощность, интервал энергии, загрузку CPU и памяти и температуру для активных серверов ЦОД, затем сохраняет измерения и итог `collector_jobs`. Пока реализован только симулятор; типы `HTTP_API`, `CSV` и `POSTGRESQL` описаны как контрактные значения, но их коллекторы ещё не подключены.


## Измерения

- `GET /api/v1/measurements` — постраничный список и фильтры `from`, `to`, `dataCenterId`, `rackId`, `serverId`, `sourceId`, `minPower`, `maxPower`, `qualityStatus`.
- `GET /api/v1/measurements/{id}` — измерение по UUID.
- `GET /api/v1/measurements/series` — хронологическая страница точек для графиков с теми же фильтрами.
- `POST /api/v1/measurements` — импорт одного измерения.
- `POST /api/v1/measurements/bulk` — атомарный пакетный импорт до 1000 измерений.

Списки принимают `page`, `size`, `sort`; размер страницы ограничен 100. Пакет отклоняется целиком при невалидном DTO или отсутствующем сервере/источнике. Временные границы и диапазон мощности проверяются до запроса.


Статусы и переходы задокументированы в [`docs/architecture/monitoring-statuses.md`](../../docs/architecture/monitoring-statuses.md).
